# zbm-clevis

Automatic unlock of a ZFS-native-encrypted root from inside ZFSBootMenu,
using [Clevis](https://github.com/latchset/clevis): a ZBM `load-key.d` hook
feeds `clevis decrypt` into `zfs load-key`, and falls through to ZFSBootMenu's
normal passphrase prompt on any failure, with dropbear listening so you can
unlock over SSH. No plaintext key is stored anywhere. ZFSBootMenu's rollback,
boot-environment selection and recovery shell are untouched.

The Clevis pin used here, and the reason this exists, is **Tang**: the machine
then boots zero-touch while it can reach a Tang server on a network you
control, and waits at the prompt anywhere else. The hook does not care which
pin the JWE names; Tang is the reference design, not the mechanism.

## The design in one screen

* **Clevis** is the mechanism. `clevis encrypt <pin>` turns the pool
  passphrase into a **JWE** whose decryption depends on the pin's policy;
  `clevis decrypt` reads the pin name from the JWE header and dispatches to
  whichever `clevis-decrypt-<pin>` binary is present. The JWE is baked into
  the ZBM image at `/etc/zbm-clevis/clevis.jwe`.
* **The hook** (`hooks/load-key.d/10-clevis-tang.sh`) runs in ZFSBootMenu's
  documented `load-key.d` stage: `timeout N clevis decrypt < jwe | zfs load-key
  -L prompt "$ZBM_ENCRYPTION_ROOT"`, exit 0 regardless. ZBM then re-checks
  `keystatus` and prompts if the key is not loaded. Every failure path lands on
  the same prompt; that fall-through *is* the design. The hook is pin-agnostic.
* **Pins in the image:** `tang`, `sss` and `null`, so a single Tang or a
  Shamir threshold over several works. `tpm2` is possible (add
  `clevis-decrypt-tpm2`, `tpm2-tools` and the TPM modules) but untested here,
  and it forfeits the network-bound property below.
* **Tang, the reference pin.** A stateless key-exchange server
  (McCallum-Relyea) that never holds the secret; it is only a thing that must
  be *reachable*. The `net` hook and its DHCP timeout exist for this pin alone.
  Tang itself is not part of this repo; `examples/tang-docker/` is one way to
  run it.
* **Threat model with Tang:** JWE (on an unencrypted ESP) + reachability of
  Tang = passphrase. Bind Tang to a trusted network only. A machine stolen from
  the same LAN as its Tang unlocks itself. **Do not put a mesh VPN inside ZBM to
  reach Tang**: that makes the machine unlock from anywhere with internet,
  which is precisely the property this removes. For a second site, run a
  second Tang there and bind with `sss` at threshold 1.
* **Dropbear** rides in the same image on a non-22 port for manual unlock:
  `ssh -p 222 root@host`, then run `zfsbootmenu`.

## What is here

| Path | What |
|---|---|
| `build.sh` | `./build.sh dropbear` (net + dropbear) or `./build.sh clevis` (+ Clevis). Stages into `.stage/`, never mutates tracked files, refuses to build without `hostid`, `dropbear/root_key`, and (for clevis) the JWE. |
| `local.conf.example` | Every per-machine knob, documented: NIC name, DHCP timeout, dropbear port, extra kernel modules, JWE path, clevis timeout, extra ZBM kernel args, and how to produce `hostid`. |
| `config.yaml`, `zbm-builder.conf`, `zbm-builder.sh` | Stock zbm-builder inputs. `zbm-builder.sh` is vendored unmodified from ZBM v3.1.0 (MIT). |
| `mkinitcpio.conf.d/` | Drops `autodetect` (host-generic image), adds `net` + `dropbear` hooks, adds the clevis binaries and the JWE. |
| `rc.d/` | Container-time scripts: populate `/etc/dropbear` (copy, not symlink; see gotchas), patch a DHCP timeout into the `net` hook, stage the JWE and the clevis timeout. |
| `hooks/load-key.d/10-clevis-tang.sh` | The hook. Byte-identical to what ships in the image. |
| `scripts/enroll.sh` | Run as root on the target: `clevis encrypt tang` (or `sss` over several URLs) from the keyfile, with a `cmp` round-trip. Never prints key material. |
| `scripts/install-image.sh`, `scripts/promote-image.sh` | Install as a **new** ESP file with its own boot entry, restore `BootOrder` verbatim, arm a one-shot `BootNext`; promote to default only after a verified boot, refusing unless a byte-identical backup of the outgoing loader exists. |
| `scripts/check-clean.sh` | Refuses tracked private keys, SSH pubkeys, JWEs, private/CGNAT IPs. Run before any push. |
| `test/` | libvirt harness: build a throwaway UEFI disk with an encrypted test pool, boot the image, screenshot, poll keystatus over dropbear, run the failure matrix. `verify-in-image.sh` inspects an image offline. |
| `examples/tang-docker/` | A minimal Tang container (debian + tang 15, standalone `tangd -l`). Tang itself is not part of this repo. |
| `upstream/` | Two things that belong elsewhere: the hook as a ZBM `contrib` candidate, and a `net_timeout` patch for mkinitcpio-nfs-utils. |

## What was verified, and what was not

Verified on one Lenovo M720q (Intel I219-V, Ubuntu 24.04, ZFS 2.2, ZBM 3.1.0
built from the Void-based container with kernel 6.18):

| Scenario | Result |
|---|---|
| Real box, Tang reachable, cold boot | Ubuntu SSH up **53 s** after `reboot`, no input |
| Real box, Tang stopped | ZBM prompt with dropbear on 222 at **+24 s**; recovered zero-touch after starting Tang and `reboot -f` over dropbear |
| VM, Tang reachable | key loaded **+19.4 s** from power-on |
| VM, Tang refused | prompt at **+16-18 s** |
| VM, Tang blackholed (packets dropped) | prompt at **+35.7 s** (clevis timeout 15 s) |
| VM, link down | prompt at **+36-39 s** (DHCP timeout 20 s) |

Not verified: any other hardware, any pin other than `tang`, the `sss`
two-site path end to end, `zbm.hookroot`, podman (only docker was used),
anything after ZBM 3.1.0 / clevis 23.

## Gotchas that cost real time

* mkinitcpio's `autodetect` inspects the **build** host, so an image built on A
  loses B's NIC driver. Dropped; image grows from ~62 to ~100 MiB.
* klibc `ipconfig` retries DHCP **forever**; the stock `net` hook passes no
  `-t`. Patched at build time; patch offered upstream.
* `clevis-decrypt-tang` gives curl **no timeout**. Refused connections fail in
  milliseconds; dropped packets hang. Hence `timeout` in the hook.
* mkinitcpio `add_file` **resolves symlinks**. Symlinking `/etc/dropbear` to
  the build dir ships an image with no host keys on port 22. Copy instead.
* Lenovo firmware **rewrites `BootOrder`** on `efibootmgr -c`. Save it first,
  restore verbatim, verify.
* Drivers built into the kernel (`CONFIG_E1000E=y` in Void's kernel) have no
  `.ko` and will look "missing" from the image. They are not.
* `zfs load-key -L prompt` reads stdin to the first newline, so a trailing
  newline in the keyfile does not matter. `cmp` against the keyfile is still
  the check.
* The pool's on-disk hostid, the booted OS's `spl_hostid=`, and `/etc/hostid`
  can all disagree on a real machine. ZBM's default import policy copes, but
  bake the pool's value.

## If you are adapting this

The per-machine surface is exactly: `local.conf`, `hostid`,
`dropbear/root_key`, the dropbear host keys (generated on first build, written
back to `dropbear/`, gitignored), and the JWE. Everything else is generic.
Suggested order: build the dropbear-only image, prove DHCP and SSH in a VM or
on the box, then enroll, build the clevis image, run the failure matrix in the
VM, install with the one-shot `BootNext` pattern, promote only after a verified
zero-touch boot. Keep the stock ZBM image as a backup boot entry, always.

Ideas not implemented: `zbm.hookroot` to keep hook + JWE on the ESP so key
rotation is a file copy, not a rebuild; a `command=` wrapper if Tang key
rotation is automated.
